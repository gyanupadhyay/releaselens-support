# Architecture and trust boundaries

The VS Code entrypoint activates a workspace controller. UI prompts and webviews remain in the extension; credentials are accessed through a SecretStorage wrapper. A CommandSession reserves ownership synchronously before asynchronous secret retrieval, owns cancellation and process cleanup, and prevents overlapping CLI commands. A workflow captures its workspace once; changing the active editor does not retarget an in-flight command.

The extension invokes the bundled CLI through literal process arguments and validates JSON responses at the process boundary. The CLI validates strict project schemas and supplies the platform adapter registry to the core engine. Core depends on the Adapter interface, not concrete browser or Android implementations. An architecture regression test rejects core imports from adapters or VS Code. Packages are private source workspaces, bundled into one extension; they are not advertised as independently published libraries.

The engine owns planning, provenance, project locking, evidence aggregation and media composition. Platform adapters own browser/Maestro execution and observation timestamps. Media output is based on successful observed assertions. Web uses a pinned Playwright runtime, bounded recording and fail-closed redirect handling. Android uses a per-user device lease and validates its own recorder PID against the unique remote output path before sending SIGINT. It does not discover and kill arbitrary device-wide recorders.

Project lock updates and recovery are serialized with an atomic leased directory lock. The long-lived run lock includes PID and nonce. Dead coordinator/device leases expire; project recovery still checks process liveness before changing manifests. The state directory is user-owned; cooperating projects share the default device lease. These controls protect against accidental concurrent use, not an adversary controlling the same OS account or adb server.

Only trusted local workspaces and reviewed flows are supported. Maestro YAML is executable automation with the user's tool privileges. URL/path validation does not turn a hostile app into a safe sandbox. A deployment receipt is an untrusted claim until GitHub deployment/check records and the running build are verified. Android hashes are bound to a trusted deployment pipeline's server-side artifact attestation; users with deployment-write privileges remain trusted producers.

Source fingerprints cover tracked and nonignored source files, including binary assets, XML, Kotlin, workflows and Gradle launchers. Release evidence must match that fingerprint and be fresh. CI tests Windows x64, Linux x64 and macOS Intel; real hosts test the extracted bytes of each audited VSIX. The exact Windows archive tested is the archive submitted to Marketplace. Real Flutter web and Android sample acceptance are additional gates. Public documentation describes unverified platforms separately.

Remaining architecture work is incremental maintainability: the controller can be split further as UI workflows grow, and independently versioned packages would need explicit exported APIs and separate builds. Neither is represented as an independently supported SDK today. No security review proves the absence of vulnerabilities; release readiness is limited to the documented pre-release scope and executed checks.
